HTTP协议

HTTP（HyperText Transfer Protocol，超文本传输协议） 是OSI模型的最顶层——应用层的一个协议。它是一个客户端（用户）和服务端（网站）之间请求和应答的标准，通常使用TCP协议。

建立连接——三次握手

HTTP的连接基于FTP的三次握手。建立连接和中止连接时，通常需要用到五个重要的值：

名称 作用
SYN（Synchronize）标志位 标志位被设置为1，表示请求连接
ACK（Acknowledgment）标志位 标志位被设置为1，表示确认已收到对方的连接请求
FIN（Finish）标志位 标志位被设置为1，表示请求中止连接，同时自身不再发送数据
seq（Sequence Number） 标识传输数据的顺序
ack（Acknowledgment Number） 告知接收方数据的确认情况

除去FIN标志位的剩余四个都是建立连接需要用到的。seq序列号和ack确认号可以通过图示来清晰展现其作用：

sequenceDiagram
 autonumber
    participant C as Client
    participant S as Server

    C-)S: SYN=1, ACK=0, seq=x, ack=0
 S-)C: SYN=1, ACK=1, seq=y, ack=x+1
 C-)S: SYN=0, ACK=1, seq=x+1, ack=y+1

SYN包用于发起一个连接请求，而ACK包用于告知接收对方的连接请求。在第二次握手时，服务端发送了一个SYN-ACK包，表示接收了客户端的连接请求，同时请求连接到客户端。

  • 第一次握手：发送SYN包，证明客户端的发送能力正常；
  • 第二次握手：发送SYN-ACK包，证明服务端的发送能力和接收能力正常；
  • 第三次握手：发送ACK包，证明客户端的接收能力正常。

在连接建立（Established）之后，就能够正常使用HTTP报文进行通信了。

中止连接——四次握手

中止连接需要多一次握手：

sequenceDiagram
 autonumber
    participant C as Client
    participant S as Server

    C-)S: FIN=1, ACK=0, seq=x, ack=0
 S-)C: FIN=0, ACK=1, seq=y, ack=x+1
 S-)C: FIN=1, ACK=1, seq=z, ack=x+1
 C-)S: FIN=0, ACK=1, seq=x+1, ack=z+1
  • 第一次握手：发送FIN包，表示客户端不再发送数据（但是仍然能够接收数据）；
  • 第二次握手：发送ACK包，表示服务端确认收到客户端的中止请求，但是仍然能够向客户端发送数据；
  • 第三次握手：发送FIN包，表示服务端不再发送数据；
  • 第四次握手：发送ACK包，表示客户端确认收到服务端的种植请求，连接关闭。

为什么不把第二次握手和第三次握手合并？即使客户端不再发送数据，但是仍有可能接收到不完整的数据。服务端收到关闭请求后，仍然需要把完整的数据传输到客户端，因此设计第二次和第三次握手之间的间隔，让数据能够传输完毕再关闭，以免意外的数据丢失。

HTTPS协议

HTTPS（HyperText Transfer Protocol Secure） 是HTTP的增强版，旨在保障报文数据在传输过程中的安全性。HTTP协议是纯文本协议，也就是说在传输过程中不存在任何的加密，经过的路由或者服务器可以轻松地获取到数据中的内容，这让一些敏感数据很容易泄露。因此我们需要在通讯过程中把数据加密。

科学家发明了一类算法叫做 对称加密算法（Symmetric Encryption Algorithm），它只有一把密钥，同时用于加密和解密。只要协商好使用的算法，并且在服务端和客户端各自准备好密钥，就能进行安全的数据传输。但是这样的问题是，如何分发私钥？

一个典型的例子是WiFi的密码连接。WiFi使用WPA2/WPA3协议，其中用到AES算法，是一种对称加密算法，而WiFi密码本身就是一把密钥，这个密码是你向WiFi持有者私密询问得到的，只要不告诉别人，别人就不能使用或者从WiFi传输过程中窃取你的信息。

但是，在互联网通信上，没有这样的物理媒介，通过私密的对话来进行密钥的获取，因为使用这样的媒介本身就是一种加密和解密。非对称加密算法（Asymmetric Encryption Algorithm） 在此呈现。非对称加密不同于对称加密，拥有两把钥匙，私钥（Private Key）和公钥（Public Key）。它的特点是，用私钥加密的数据只能用公钥解密，用公钥加密的数据只能用私钥解密。同时，公钥也不能解密由其加密的数据，私钥也同理。

为什么非对称加密的公钥加密可以私钥解密？

我们以著名的RSA算法为例。RSA算法的步骤：

  • 寻找两个大质数 ppp 和 qqq；
  • 计算乘积 n=pqn = pqn=pq；
  • 计算Euler函数 φ(n)=φ(p)φ(q)=(p−1)(q−1)\varphi(n) = \varphi(p)\varphi(q) = (p - 1)(q - 1)φ(n)=φ(p)φ(q)=(p−1)(q−1)；
  • 随机指定一个质数 eee，由于它在模 φ(n)\varphi(n)φ(n) 的乘法群，一定能够找到其模 φ(n)\varphi(n)φ(n) 下的唯一逆元 ddd；

我们获得的公钥就是 (n,e)(n, e)(n,e)，私钥就是 (n,d)(n, d)(n,d)。对于任何与 nnn 互质的数 MMM，把它视为信息，由Euler定理：

Ce≡(Md)e≡Mde≡Mkφ(n)+1≡M(mod⁡n),C^e \equiv (M^d)^e \equiv M^{de} \equiv M^{k\varphi(n)+1} \equiv M \quad (\operatorname{mod} n),Ce≡(Md)e≡Mde≡Mkφ(n)+1≡M(modn),

即 CCC 是密文，可以发现取幂就是加密和解密操作，并且这个操作可以先做 ddd 的幂，也可以先做 eee 的幂。

排除掉和 nnn 不互质的元素，一方面是不满足Euler定理，另一方面它是环 Z/nZ\Bbb{Z}/n\Bbb{Z}Z/nZ 的零因子，可以证明它在进行有限次取幂操作后为 000。

在TCP三次握手建立（稳定的）连接后，我们需要额外一次握手——SSL/TLS握手。SSL是一种协议，它表示在这次握手中需要进行的操作，来确保之后的传输是安全的。目前来说，有非常多的库实现了这个协议，比如著名的开源库OpenSSL。

要让双方都能持有对方的公钥，我们可以尝试给出下面的流程：（🟡代表私钥，🟢代表公钥，私钥和公钥最开始均在每个端手中）

这个过程比刚才安全多了。中间的路由或者代理只能拿到服务端公钥和被服务端公钥加密过的客户端公钥，而之后的数据均用公钥加密，只有私钥才能解密，保障了安全。

可以看到，如果代理服务器在握手过程中拦截了公钥，并把自己的公钥发给客户端，反之也把自己的公钥发给服务端，那么之后的加密通信的过程中，它仍然能够截获并解密数据甚至于修改数据，并且很可能双方都不知情，这是非常危险的。这就是 中间人攻击（MITM attack，Man In The Middle Attack）。这里的关键在于把公钥直接传递给客户端是不安全的。

这时候 证书（Certificate） 就派上用场了。它就好比一个权威的机构（CA），颁发一个证书给服务器说明了这个服务器是可信任的。首先，一个服务器网站需要向CA机构提供网站的一些基本信息，其中包括服务端的公钥。CA会把这些信息用CA私钥加密，形成CA证书，发放给网站。同时，CA还会把公钥发放给客户端的浏览器，通常是内置在浏览器中的。一次正常的握手如下：

 P--XC: 无法发送包含<br>🟢P的证书

除非代理服务器也申请了自己CA证书，否则客户端将认为连接不安全而拒绝连接。但是，如果客户端之前进行过服务器的连接，那么通过比对上次的CA证书，就能辨别出服务器的真伪，也会拒绝连接。而且，即使没有证书，现代浏览器也会监控异常流量，通过分析 HTTP 或 HTTPS 流量的大小、模式或时间间隔，也可能会检测到中间人代理服务器的存在。

最终这一整套由CA机构参与在内的协议就被称为HTTPS协议，所有的安全通信建立在可信任的证书颁发机构之上。所以，CA机构一定要足够安全，如果它的私钥泄露，后果将不堪设想。

顺带一提，WebSocket也有对应的安全版本WSS，它只是相当于从本来的HTTP升级协议请求修改为HTTPS升级协议请求，即在安全环境下进行协议升级。
